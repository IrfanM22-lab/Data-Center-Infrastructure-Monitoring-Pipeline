# Data Center Infrastructure Monitoring Pipeline

A data engineering pipeline that ingests real server telemetry, validates it, transforms it, and
loads it into a queryable warehouse — built to close a specific gap: the data science portfolio this
project sits in was entirely modeling notebooks that started from an already-clean CSV. This project
builds the layer that produces that clean CSV in the first place.

## What this is

Real AWS CloudWatch server metrics (CPU utilization, network throughput, disk I/O, RDS CPU) from four
production-style instances, run through a full **Extract → Validate → Transform → Load → Orchestrate →
Monitor** pipeline, with an anomaly-flagging example showing the warehouse output being consumed
downstream.

- **Data**: real telemetry from the [Numenta Anomaly Benchmark](https://github.com/numenta/NAB)
  (`data/raw/`), not synthetic
- **Config**: source registry externalized to `config/sources.yaml` — onboarding a new server means
  editing YAML, not code
- **Warehouse**: a star-schema SQLite database (`warehouse/infra_monitoring.db`) — dimension/fact
  tables, the standard pattern for BI-facing warehouses
- **Orchestration**: a real, deployable Airflow DAG (`orchestration/infra_monitoring_dag.py`)
- **Quality gates**: duplicate, null, and out-of-range checks, proven against both real data issues
  and deliberately injected synthetic corruption

## Running it

```bash
pip install -r requirements.txt
jupyter notebook infra_monitoring_pipeline.ipynb
```

Run all cells top to bottom. The pipeline is deterministic — re-running it end to end reproduces the
same figures (16,826 real rows extracted, 11 real duplicate readings caught, 14 real gaps filled).

## Known simplifications

This project demonstrates the reasoning and stages of a real pipeline at a scale that's runnable and
inspectable in one sitting — it is not a claim that this is how a data center actually runs
infrastructure monitoring at production scale. Specific gaps, stated plainly:

**Some numbers here are illustrative, not derived from a benchmark.** The general patterns used
(a validation gate rejecting bad records, an alert threshold on reject rate, a rolling window for
anomaly scoring, retries with backoff) are genuinely standard data engineering practice. The specific
parameter values attached to them are not: the 5% reject-rate alert threshold in the Airflow DAG, the
1-hour rolling window, and the `|z| > 3` anomaly cutoff were all chosen for this demonstration, not
pulled from a real operational cost model. In a real deployment these would be tuned against actual
false-positive/false-negative costs, not set once and left alone.

**Scale and tooling would differ substantially in a real environment:**

| This project | Typical production equivalent |
|---|---|
| Static CSV files | Streaming ingestion (Kafka/Kinesis) or push-based agents (Prometheus, CloudWatch agent) |
| pandas | Spark or Flink at volumes that don't fit in memory |
| SQLite | A cloud warehouse (Snowflake/BigQuery/Redshift) or a time-series DB (InfluxDB, TimescaleDB) — metrics workloads like this usually suit a TSDB better than a general warehouse |
| Hand-rolled validation checks | Great Expectations or dbt tests, often paired with a data observability tool |
| Transform-then-load (ETL) | Often reversed to ELT — load raw, transform in-warehouse with dbt/SQL |
| A DAG file in this repo | Deployed via CI/CD, monitored with alerting wired into PagerDuty/Opsgenie |

The Airflow DAG in `orchestration/` is real, correct, deployable code — it is not executed as part of
this repo, since there's no persistent Airflow scheduler available in a notebook/portfolio context.

## What's real vs. simulated

- **Real**: all four telemetry sources, their timestamps and values, the duplicate/gap issues the
  pipeline catches, all reported metrics
- **Simulated**: the "asset registry" metadata (site/rack/instance naming) laid on top of the real
  metric values, and three deliberately injected bad rows (tagged `SYNTHETIC_INJECTED`) used to prove
  the validation gate catches null/out-of-range values it wouldn't otherwise see in this clean dataset
